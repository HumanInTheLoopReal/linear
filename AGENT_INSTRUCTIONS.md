# Detailed Agent Instructions for linear-cli Development

**New here? [README.md](README.md) covers what this tool is and how to run it.**
**For architecture invariants and layer rules, see [AGENTS.md](AGENTS.md).**

This document is the deep-dive operational guide. It layers operational
concerns (workflows, visual design conventions, non-interactive shell
rules) on top of `AGENTS.md`. When a fact lives in `AGENTS.md`, this
file points at it instead of duplicating.

## 1. Read first

- [`AGENTS.md`](AGENTS.md) — architecture, layer rules, decision tree,
  anti-patterns. Read this **before** writing any source code.
- [`CLAUDE.md`](CLAUDE.md) — thin pointer; the ground rules are there.
- [`docs/adr/`](docs/adr/) — cross-cutting architectural decisions with
  their non-obvious rationale. Read the relevant ADR before changing
  one of the decisions it covers.

## 2. Development guidelines

### Toolchain

- **Node**: see `package.json` `engines` field (currently `>=22`).
  Do **not** hard-code a Node version in agent prompts or in this doc;
  rely on `engines` so the source of truth tracks the repo.
- **Package manager**: npm (lockfile committed).
- **Formatter / linter**: Biome (`npm run check` for auto-fix,
  `npm run check:ci` for CI-mode verify).
- **Tests**: Vitest (`npm test`). Coverage report: `npm run test:coverage`.
- **GraphQL codegen**: `npm run generate` regenerates `src/gql/`.
  **Never edit `src/gql/` by hand** — it is generated.
- **USAGE.md**: generated by `npm run generate:usage` during the build
  step. It is git-ignored. Do not commit it.

### Source layout

See [`AGENTS.md` § "File Map"](AGENTS.md#file-map) for the canonical
layout. Headline: `src/{client,resolvers,services,commands,common}`,
`graphql/{queries,mutations}/*.graphql`, `tests/{unit,integration}`.

### Testing workflow

Mock one layer deep. The patterns are in
[`AGENTS.md` § "Testing"](AGENTS.md#testing).

Quick reference:

| Test target | Mock | Example file |
|---|---|---|
| Resolver | `LinearSdkClient` (mock `sdk.*`) | `tests/unit/resolvers/*.test.ts` |
| Service | `GraphQLClient` (mock `request`) | `tests/unit/services/*.test.ts` |
| Common | No mocks (pure functions) | `tests/unit/common/*.test.ts` |
| Command | Stub both via fake context | `tests/unit/commands/*.test.ts` |

**Coverage minimum**: happy path + primary error case per function.

**Integration tests** (`tests/integration/`) need
`LINEAR_API_TOKEN` set and a real Linear workspace. They are skipped
automatically when the token is absent, so they do not block local
development.

```bash
npm test                              # unit suite
npx vitest run tests/unit/resolvers   # narrow to one layer
npm run test:integration              # requires LINEAR_API_TOKEN
```

## 3. Before committing

Run all four gates. CI runs the same four, so failing any locally
guarantees a CI failure:

```bash
npm run check:ci       # biome format + lint (no auto-fix)
npx tsc --noEmit       # strict TypeScript check
npm test               # unit tests
npm run build          # codegen + tsc + USAGE.md regeneration
```

If you changed `.graphql` files, ensure `npm run generate` ran before
`tsc`. If you changed `DomainMeta` exports or command registration,
ensure `npm run generate:usage` was invoked (the `build` script chains
it).

## 4. Commit message convention

Conventional Commits are required and enforced by commitlint via
lefthook:

```
<type>(<scope>): <subject> (<issue-id>)

<optional body explaining why>

Refs <issue-id>
```

Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`,
`build`, `ci`, `style`, `perf`.

**Include the Linear issue ID** in the commit subject line in
parentheses (`ENG-123`) or in a trailer (`Closes ENG-123`, `Refs ENG-123`,
`Part of ENG-123`). This:

- Lets `linear` cross-reference commits to issues for auto-close
  bookkeeping (see `prepare-commit-msg` hook installed by
  `linear hooks install`).
- Matches the trailer vocabulary the `post-commit` hook scans.

**No AI co-author trailers.** Do not add `Co-authored-by:` lines for
AI assistants. Human co-authors are fine.

## 5. PR-by-default workflow

linear-cli uses a PR-based workflow on `main`:

- Work on a feature branch.
- Push the branch.
- Open a PR against `main`.
- `gh pr create` is the normal path.

Direct push to `main` is reserved for:

- Release tags (the publish flow lives in [`RELEASING.md`](RELEASING.md)).
- Narrow operational fixes (typo, broken link).

When in doubt, open a PR.

### Branch naming

Use short, kebab-cased branch names rooted in the issue ID when
practical:

```
ENG-123-add-stealth-flag
fix-prepare-commit-trailer
docs-releasing-runbook
```

## 6. External contributor PRs

Until [`PR_MAINTAINER_GUIDELINES.md`](PR_MAINTAINER_GUIDELINES.md)
lands, the working policy is:

- Treat external PRs with respect and keep attribution intact.
- Absorbing or reshaping a contribution beats rejecting it.
- A rewrite needs a reason posted on the original PR, and the
  contributor's design or tests credited in your commits through
  `Co-authored-by:` trailers.
- Before implementing related work, run the read-only preflight: search
  open PRs first (`gh pr list --search "<topic>"`).

A full maintainer policy lands when external PR volume warrants the
formal document. For now: defer to community-first instincts and
attribute generously.

## 7. Landing the plane

"Let's land the plane" is a request to finish the session properly, and it
means every step below, in order. Nothing is landed while work sits
unpushed. Offering to push, or announcing that you are ready to push, is
not landing it.

1. **Write down what is left.** File follow-up issues for remaining work:

   ```bash
   linear create "..." -t task -p 2 --json
   ```

2. **Run the gates**, if any code changed:

   ```bash
   npm run check:ci
   npx tsc --noEmit
   npm test
   npm run build
   ```

   A failure here is not a footnote. File it at P0 or P1 and fix it before
   going further.

3. **Bring Linear up to date.** Close what finished, move what moved:

   ```bash
   linear close <id> --reason "Completed"
   linear update <id> ...
   ```

4. **Push. Every command, not the first two:**

   ```bash
   git pull --rebase
   git push
   git status   # must report up to date with origin/main
   ```

   Stopping short of a successful push strands the work on one machine.
   That matters more than it sounds: the user may have several agents
   working in parallel, and unpushed work silently breaks their
   coordination. A rejected push is something to resolve and retry, not a
   result to report.

5. **Tidy the local git state:**

   ```bash
   git stash clear
   git remote prune origin
   ```

6. **Confirm the tree is clean.** Everything committed, everything pushed,
   nothing untracked left behind.

7. **Set up the next session.** Pick the follow-up issue that should come
   next and write the prompt to resume it:

   > "Continue work on `ENG-N: <title>`. <one-line context + next step>."

Close by reporting what was completed, the follow-up issues you filed with
their IDs and titles, how the gates came out, explicit confirmation that
everything is pushed, and the resume prompt from step 7.

## 8. Agent session workflow

### Update issues with flags, never an interactive editor

linear-cli does not ship a `linear edit` interactive flow — every update
takes flags. This is intentional: agents can drive the CLI without an
attached TTY.

```bash
linear update <id> --title "new title"
linear update <id> --description "new description"
linear update <id> --state "in_progress"
linear update <id> --assign-self
linear update <id> --priority 1
linear update <id> --add-label bug
```

For long descriptions with special characters (backticks, `!`, nested
quotes), prefer stdin or `--body-file`:

```bash
# Pipe via stdin
echo 'Description with `backticks` and "quotes"' | linear create "Title" --stdin

# Use --body-file for longer content
linear create "Title" --body-file=description.md
```

### Read execution metadata before prose

When enacting a linear issue, inspect the structured fields before
reading description or notes — these decide execution mode, model,
reasoning level, parallel group:

```bash
linear show <id> --json | jq '.data | {id, identifier, title, state, priority, description}'
```

Use the description for work scope and the comments for rationale or
fallback context. When the issue has labels like `execution:model:opus`
or `execution:reasoning:high`, treat them as authoritative execution
hints — a running subagent cannot change its model after launch.

### Use `--json` for parsing

Read-only verbs flip to a stable JSON envelope under `--json`:

```bash
linear --json ready
linear --json show <id>
linear --json issues list --limit 50
```

The JSON contract is the durable agent interface. Text output is
intentionally tuned for humans and may change shape between versions.
**Never parse the text output.**

## 9. Visual Design System

New CLI output follows the conventions below. They exist so that output
stays scannable at a glance instead of demanding to be read.

### No emoji-style icons

Colored emoji blobs (🔴🟡🟢) are not how this CLI marks priority or status.
They render inconsistently across terminals and they draw the eye to
everything at once, which is the opposite of what an icon is for.

Use small Unicode symbols instead, colored semantically through chalk and
the project's style helpers.

### Status icons

```text
○ open        available now         (white/default)
◐ in_progress someone is on it      (yellow)
● blocked     waiting on a blocker  (red)
✓ closed      done                  (muted gray)
❄ deferred    parked until later    (blue/muted)
```

### Priority icons and colors

A priority renders as a filled circle followed by its label, `● P0`, with
the color carrying the weight:

| Priority | Color | Reads as |
|---|---|---|
| `● P0` | red, bold | critical, urgent |
| `● P1` | orange | high |
| `● P2` through `● P4` | default text | normal |

### Issue-type colors

- `bug`: Red (problems need attention).
- `epic`: Purple (larger scope).
- Others: default text.

### Design principles

1. Small Unicode symbols, never emoji blobs.
2. Color carries meaning, so spend it on what the reader can act on. If
   everything is colored, nothing is.
3. Let finished work recede into muted gray.
4. An icon scans faster than a word. Prefer it where one exists.
5. The same icon means the same thing in `list`, `tree`, `show`, and
   everywhere else.
6. Hierarchies use tree connectors: `├──`, `└──`, `│`.
7. Leave out what the reader already knows. `needs:1` is noise when the
   one thing it needs is the parent epic.

### Where styles live

Output formatters live next to their commands in `src/commands/`.
Shared styling primitives live in `src/common/output.ts`. When adding a
new status / priority / type, update the style maps in `output.ts`
rather than inlining colors at the formatter call site.

## 10. Non-interactive shell rules

Agents must not invoke commands that hold a TTY or wait on a pager.
The `.claude/hooks/block-interactive-cmds.sh` hook enforces this for
Claude Code sessions, but the policy applies regardless of the agent
runtime.

**Banned patterns:**

- `git commit` without `-m` (opens `$EDITOR`).
- `git rebase -i` (interactive rebase).
- `git add -i` (interactive add).
- `less`, `more`, `man` (pagers).
- `npm init` without `-y` (interactive prompts).
- Any `linear` command with an `--interactive` flag if one is added.

**Required substitutions:**

- `git commit -m "..."` (or HEREDOC for multi-line messages).
- `git log --no-pager ...` (or pipe to `cat`).
- `gh pr view <n> --json ...` (instead of the interactive viewer).
- Use `--json` flags wherever a verb offers one.

When an `agent` discovers it cannot complete a task without a TTY,
the correct response is to fail fast and surface that the workflow is
not non-interactive-compatible — not to attempt the interactive path.

## 11. Storage / source-of-truth boundary

Linear is the source of truth. Do not cache Linear state locally.

- **Read path**: every read should go through a `linear` command.
  Re-fetch on session resume; do not assume state from prior cached
  reads.
- **Write path**: every write goes through `linear` — never edit the
  GraphQL API directly outside the CLI's services.
- **Auth resolution**: the precedence chain (env var → `~/linear/token`
  → legacy `~/.linear_api_token`) is documented in
  [`AGENTS.md` § "Auth resolution"](AGENTS.md#auth-resolution). Do not
  duplicate the precedence rules here.

For scripts that need to verify auth before invoking other commands:

```bash
linear info > /dev/null 2>&1 || {
  echo "linear-cli is not authenticated; run 'linear auth login' first."
  exit 1
}
```

`linear auth login` is interactive (TTY-only). Scripts must rely on
pre-existing auth or fail clearly when it is missing.
